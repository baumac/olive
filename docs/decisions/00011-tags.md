# Motivation
[motivation]: #motivation

Decision 00004 gives restaurants and recipes free-form tags.
Each subject keeps its tags as strings. No list of all tags exists.

A user who adds a tag does not see the tags of other users.
The user then types `woodfired` when `wood-fired` already exists. The tag filters miss one of the two.
A reader also cannot see all restaurants and recipes of one tag on one page.
A superuser who fixes a wrong tag must change each subject with it.

Expected outcome:
- each tag is one record with a unique name
- restaurants and recipes refer to the tag records
- a user still adds a new tag in the restaurant form or the recipe form
- the tag input suggests the existing tags, the most used first
- the Public API lists the tags with their counts, and it gets one tag by its name
- a tag page shows the restaurants and the recipes of one tag
- a superuser renames a tag in one place in the dashboard
- the API values of restaurants, recipes, and their versions do not change

# Scope
[scope]: #scope

In scope:
- the `tags` collection, and the `tags` relation of `restaurants` and `recipes`
- the migration from the strings to the relation
- the operations of the `tags` tag: `listTags` and `getTag`
- the tags that a save makes, and the tags that a save or a delete leaves without a subject
- the rename and the delete of a tag in the dashboard
- the tag input, the tag filter, and the tag page of the UI

Out of scope:
- the rules of a tag name, the `tags` property of subjects, and the tag filters. Decision 00004 has them.
- a rename, a merge, or a delete of a tag in the Public API. A superuser does them in the dashboard. The backlog has this rule under "Won't do".
- a description, a parent, or a synonym of a tag
- tags on reviews. Decision 00004 removed them.
- a page with all tags at `/tags`
- one list operation that returns restaurants and recipes together

# Guide-level explanation
[guide-level-explanation]: #guide-level-explanation

## A tag

```json
{
  "name": "wood-fired",
  "restaurant_count": 4,
  "recipe_count": 1,
  "created": "2026-11-27T09:12:44.318Z"
}
```

- `name` is the ID of a tag in the Public API. It has the `Tag` rules of decision 00004.
- `restaurant_count` and `recipe_count` count the subjects with the tag
- a tag without a subject does not exist for the Public API

| Operation | Route |
|---|---|
| `listTags` | `GET /tags` |
| `getTag` | `GET /tags/{tagName}` |

- both operations need no token, like `listRestaurants`. An invalid token gets `401`.
- both operations have no rate limit, like the other read operations
- `getTag` gets `404` for an unknown tag and for a tag without a subject. An invalid `tagName` gets `400`.

## The tag list

| Parameter | Values |
|---|---|
| `search` | the start of the name or of a word of the name. `fired` finds `wood-fired`. |
| `kind` | `restaurants` or `recipes`. A tag without a subject of the kind is not in the list. |
| `sort` | `-count`, the default, `count`, `name`, or `-name`. The `name` sort compares code points. |
| `limit`, `cursor` | the pages of decision 00001 |

- `search` has 1 to 63 characters. It does not need the `Tag` rules, so the UI sends the text as the user types it.
- the search ignores case and accents, like the other searches. `Cafe` finds `café`.
- a space in the search matches a hyphen. `wood f` finds `wood-fired`.
- `-count` uses the sum of both counts. With `kind`, it uses the count of the kind. `name` breaks a tie.
- a tag with exactly the name of `search` comes first in each sort. It is in the list also when only the other kind has it. The tag input then finds an existing tag before it offers a new one.

## A save with a new tag

Ana adds the restaurant "Forno" with the tags `pizza` and `wood-fired`.
`pizza` exists. `wood-fired` does not.

- the save makes the tag `wood-fired` and refers to both tags
- the response has `"tags": ["pizza", "wood-fired"]`, as before
- the create limit and the edit limit of decision 00003 count the save. A new tag adds no count.

Ana then removes `wood-fired` from "Forno". No other subject has it.
The save deletes the tag. The tag input does not suggest it again.

## The UI

- the tag input of the restaurant form and the recipe form opens a list of suggestions on focus. The list has the most used tags of the kind.
- typing changes the suggestions. Each suggestion has the name and the count.
- a text without an exact match gets the option "Add new tag ‘text’"
- an invalid text gets the suggestion of decision 00004, such as `crème-brûlée` for `Crème Brûlée`
- the tag filter of the restaurant and recipe pages has the same input. It suggests only existing tags and has no "Add new tag" option.
- each tag on a restaurant page or a recipe page links to `/tags/{name}`
- the tag page has the name of the tag, `KindSwitch`, and a section for restaurants and a section for recipes. Each section has the highest overall first, like the menu of a list in decision 00006.

## A superuser fixes a tag

Two users added `woodfired` and `wood-fired`.
The superuser opens `woodfired` in the dashboard and changes each of its subjects to `wood-fired`.
The superuser then deletes `woodfired`.

A rename to a name that exists gets the error of the unique index. A merge needs the steps above.
The relation picker of the dashboard shows only existing tags. A superuser makes a new tag in the `tags` collection first.

# Implementation Details
[implementation-details]: #implementation-details

## Collections

| Collection | Fields |
|---|---|
| `tags` | `name`, `name_key`, `created` |

- `name` is a required text field with the `Tag` pattern and a maximum of 63. `idx_tags_name` is a unique index on it.
- `name_key` is the name in lowercase without the marks of category `Mn`. A record hook sets it on each save. It serves the search of `listTags`.
- the API rules are `null`. Only superusers use the collection through the PocketBase API.
- `tags` of `restaurants` and `recipes` is a relation to `tags` with a maximum of 20. It has no cascade delete.
- an empty relation is `[]` in the database. The API returns `null`, as decision 00004 requires.

## Tag tables

- `restaurant_tags` and `recipe_tags` keep one row for each tag of a subject. Their `tag` column has the ID of the tag record.
- the triggers of decision 00004 keep the tables equal to the records. They read the IDs of the relation with `json_each`.
- `tags[has_any]=a&tags[has_any]=b` adds `restaurants.id IN (SELECT restaurant FROM restaurant_tags WHERE tag IN (SELECT id FROM tags WHERE name IN ('a', 'b')))`
- an unknown tag in a filter matches no subject. A filter with an invalid tag still gets `400`.
- the counts of a tag come from the tag tables. The tables have the index on `tag` from their primary key.

## The migration

`1795737600_tags.go` is the migration. `1794096000_init.go` does not change. See decision 00002.

1. It makes the `tags` collection.
2. It reads the tags of each subject into memory. It keeps only the strings of the JSON arrays.
3. It inserts one tag record for each distinct name with SQL.
4. It drops the tag triggers. SQLite refuses the field change with them.
5. It replaces the `json` field `tags` with the `relation` field `tags` at the same position. PocketBase drops the old column. PocketBase refuses a change of the type of a field.
6. It writes the IDs of each subject with SQL. The `updated` time stays, and no version is written.
7. It makes the triggers again and fills the tag tables with the IDs.

The down migration writes the names back into a `json` field in the order of the relation. It then deletes the collection.

The `snapshot` of the versions keeps the names. It does not change.

## Server

- `recordvalues.ExpandTags` loads the tag records of the relation. `recordvalues.Tags` gives their names in the order of the relation. The Public API, `searchindex`, and `Kind.Snapshot` use them. The API values and the versions do not change.
- `ExpandTags` first removes the old expand. PocketBase keeps an old expand when the relation is empty.
- `resolveTags` of `tags.go` gets the ID of each name in the transaction of a create or an update. It makes a tag record for each missing name.
- the tags come after the place check and the source check. A conflict then makes no tag.
- `resolveTags` uses `SaveNoValidate`. The spec validation checked the names. With `REVIEWS_VALIDATE_REQUESTS=false`, an invalid name stays, like the other values.
- the relation keeps its limit of 20 also without the spec validation. More than 20 unique tags get `422` with an error of `tags`.
- `idx_tags_name` stops a second record for one name when two saves make the same tag at the same time
- `restaurantguard.go` and `recipeguard.go` check the tags of a dashboard save as IDs of existing tags. They then give the names to the checks of `RestaurantCreate` and `RecipeCreate`.
- `searchindex` writes the names of the tags into the `tags` column of the search tables. The record has only the IDs.
- a record hook of `restaurants` and `recipes` deletes the removed tags without a subject. It runs in the transaction of the save or the delete. A save in the dashboard also gets it.
- `tagguard.go` gives a save of a tag in the dashboard the checks of `Tag`. These are the normalization form C and the code points of `checkTagFormat`.
- a rename of a tag in the dashboard updates the search tables of its subjects. Their `tags` column has the names. See decision 00002.
- a rename also writes a version with the source `admin` for each subject with the tag. Without it, the next version of a user shows a change of `tags`.
- a delete of a tag in the dashboard removes its ID from each subject. PocketBase 0.40 calls `SaveNoValidate` for each subject, so each one gets a version with the source `admin`.
- the record hook of unused tags deletes with SQL. PocketBase deletes the row of a tag before it saves the parents. The hook then finds no row of that tag.
- `recordvalues.ParentsWithTag` finds the subjects of a renamed tag for `history` and `searchindex`
- `listTags` keeps a tag when an `EXISTS` finds a row of it in a tag table of the kinds. The counts of the sort and the response come only for these tags.
- the exact name of the search is the first sort key, `name = search` in descending order. The cursor has its value too. The exact tag needs an `EXISTS` in any tag table.
- `nfcTags` changes the names of a create or a patch to normalization form C and drops repeats. With the spec validation off, `café` in two forms is then one tag. The limit of 20 counts the changed names.
- the search of `listTags` compares `name_key` with `LIKE 'text%'` and `LIKE '%-text%'`. The search text gets lowercase letters and loses its accents first. `%` and `_` are escaped.
- the `tags` table is small. The search reads all rows.
- `x-nfc` also changes the path parameters. `getTag` then finds `café` with `cafe` + U+0301.
- a new kind of subject adds its tag table, a count property, and a value of `kind`

## The UI

- `TagInput` follows the combobox pattern of WAI-ARIA. The input has the role `combobox`. The suggestions are a `listbox` with the name "Suggestions".
- the listbox name has no "tags". `getByLabel('Tags')` of the end-to-end tests would find it too.
- the name of each suggestion is its text, such as "wood-fired, 4 restaurants". The comma is in a `sr-only` span. An `aria-label` would differ from the visible text. Axe refuses that in WebKit.
- the prop `suggest` gets the suggestions. `tagSuggester` of `lib/tags.ts` calls `listTags` with `kind`, the default sort `-count`, and a limit of 8. `TagInput` waits 200 ms after the last key.
- `listTags` puts a tag with the exact name first, also when it is not in the most used. "Add new tag" then does not show for an existing tag.
- `tagSuggester` of a filter has `onlyUsed`. It drops an exact tag that only the other kind has. Its filter would show nothing.
- while the suggestions of a new text load, the arrow keys select nothing. The list can still show the old options. Enter then adds the typed text.
- Enter adds the selected suggestion. Without a selected suggestion, it adds the typed text. A mouse click on a suggestion keeps the focus in the input.
- the prop `allowNew` adds the option "Add new tag ‘text’". It is on by default. `FilterBar` turns it off.
- the prop `openOnFocus` shows the most used tags on focus. It is on by default. `FilterBar` turns it off, because the popover focuses the input when it opens. Typing or ArrowDown then opens the suggestions.
- without `openOnFocus`, a pick closes the list. In a form, the list shows the most used tags again after a pick.
- `TagPage.vue` has the route `/tags/:name`. Each section loads `listRestaurants` or `listRecipes` with `tags[has]` and `sort=-overall`. Each section has its own "Load more".
- a section loads its list when `KindSwitch` shows it, one time for each tag. A hidden section sends no request.
- the sections do not merge the two lists. The `overall` sort also uses the number of reviewers, so the UI cannot compare a restaurant with a recipe. See decision 00005.
- a tag name that the API refuses gets the not found page, like an unknown tag
- `ParentCard` shows the tags as text. The card is one link, and a link cannot have a link in it.
- `pagemeta.go` of `app/api/internal/webui` writes the title of the tag page. See decision 00002.
- `specs/design-system/components/TagInput` describes the suggestions and the "Add new tag" option

# Alternatives
[alternatives]: #alternatives

| Alternative | Result |
|---|---|
| The names stay in the subjects, and `tags` is only a list of the names | Not selected. A rename would change each subject with the tag. |
| Tag IDs in the Public API | Not selected. The SDKs, the UI, the filters, and the versions would change. The name is already unique. |
| Only existing tags on a subject, and a `createTag` operation | Not selected. A user would leave the form to add a tag. |
| A new tag only from the dashboard | Not selected. A superuser would need to act before each new tag. |
| One operation that lists the restaurants and the recipes of a tag | Not selected. It needs a `oneOf` of both kinds and a cursor over two tables. The UI loads the two lists. |
| One merged list of both kinds on the tag page | Not selected. The `overall` sort cannot compare a restaurant with a recipe in the UI. |
| A rename, a merge, and a delete in the Public API | Not selected. A superuser does them in the dashboard. |
| Tags without a subject stay | Not selected. The input would suggest each removed typo. |
| An FTS5 table for the search of `listTags` | Not selected. The `tags` table is small, and it needs more triggers. |
| `TagsInput` and `Combobox` of reka-ui for the tag input | Not selected. The custom combobox keeps the checks, the blur, and the Backspace of `TagInput`. |
