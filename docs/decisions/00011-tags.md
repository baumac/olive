# Motivation
[motivation]: #motivation

Decision 00004 gives restaurants and recipes free-form tags.
Each subject keeps its tags as strings. No list of all tags exists.

A user who adds a tag does not see the tags of other users.
The user then types `woodfired` when `wood-fired` already exists. The tag filters miss one of the two.
A reader also cannot see all restaurants and recipes of one tag on one page.
A superuser who fixes a wrong tag must change each subject with it.

The strict `Tag` rules also refuse `Wood Fired`, `BBQ`, `gluten_free`, and `Crème Brûlée`.
The UI suggests the valid form, but the user must type it again. Other clients get `422`.
One tag must keep one spelling, so the tag filters and the tag page find all subjects.
The API therefore accepts free text and changes it to that spelling.

Expected outcome:
- each tag is one record with a unique name
- restaurants and recipes refer to the tag records
- a user still adds a new tag in the restaurant form or the recipe form
- a user types a tag as free text. The API and the UI change it to the stored form.
- two texts that a person reads as the same tag give one tag
- the UI shows the stored form before the user adds the tag
- the tag input suggests the existing tags, the most used first
- the Public API lists the tags with their counts, and it gets one tag by its name
- a tag page shows the restaurants and the recipes of one tag
- a superuser renames a tag in one place in the dashboard
- the API values of restaurants, recipes, and their versions do not change

# Scope
[scope]: #scope

In scope:
- the `tags` collection, and the `tags` relation of `restaurants` and `recipes`
- the migration from the strings to the relation
- the rules of a tag name, and the change of a text to a tag name
- the migration of the existing names to the new rules
- the operations of the `tags` tag: `listTags` and `getTag`
- the tags that a save makes, and the tags that a save or a delete leaves without a subject
- the rename and the delete of a tag in the dashboard
- the tag input, the tag filter, and the tag page of the UI

Out of scope:
- the `tags` property of subjects and the tag filters. Decision 00004 has them.
- a rename, a merge, or a delete of a tag in the Public API. A superuser does them in the dashboard. The backlog has this rule under "Won't do".
- a description, a parent, or a synonym of a tag
- a merge of plurals, such as `pizza` and `pizzas`
- a merge of `café` and `cafe`. Accents keep tags apart.
- emoji in tags
- the case of the user, such as `BBQ`. Tags stay lowercase.
- tags on reviews. Decision 00004 removed them.
- a page with all tags at `/tags`
- one list operation that returns restaurants and recipes together

# Guide-level explanation
[guide-level-explanation]: #guide-level-explanation

## A tag

```json
{
  "name": "wood-fired",
  "restaurant_count": 4,
  "recipe_count": 1,
  "created": "2026-11-27T09:12:44.318Z"
}
```

- `name` is the ID of a tag in the Public API. It has the rules of [Tag names](#tag-names).
- `restaurant_count` and `recipe_count` count the subjects with the tag
- a tag without a subject does not exist for the Public API

| Operation | Route |
|---|---|
| `listTags` | `GET /tags` |
| `getTag` | `GET /tags/{tagName}` |

- both operations need no token, like `listRestaurants`. An invalid token gets `401`.
- both operations have no rate limit, like the other read operations
- `getTag` changes `tagName` to a tag name first. `/tags/Wood%20Fired` gets `wood-fired`.
- `getTag` gets `404` for an unknown tag and for a tag without a subject. A `tagName` without a letter or a digit gets `400`.

## Tag names

A stored tag name has 1 to 63 characters in lowercase. It has words with single hyphens between them.
Each word starts with a letter or a digit of any script. Combining marks, such as the vowel signs of Devanagari, can follow.

The API accepts free text. It changes the text to a tag name in these steps:

1. It changes the text to Unicode normalization form NFKC. Fullwidth letters, ligatures, and superscript digits become plain letters and digits.
2. It changes the text to lowercase. `İ` becomes `i` without the combining dot.
3. It removes the default ignorable code points, such as variation selectors, zero-width joiners, and soft hyphens.
4. It changes each run of characters that are not letters, marks, or digits to one hyphen. These are spaces, underscores, apostrophes, punctuation, symbols, and emoji.
5. It removes the marks at the start of each word, and the hyphens at the start and the end.
6. It changes a `σ` at the end of a word after a letter to `ς`. The lowercase of `Σ` does not know its place in the word.

| Text | Tag name |
|---|---|
| `Wood Fired` | `wood-fired` |
| `wood_fired`, `wood--fired`, ` Wood-Fired! ` | `wood-fired` |
| `BBQ` | `bbq` |
| `Crème Brûlée` | `crème-brûlée` |
| `ＰＡＳＴＡ` | `pasta` |
| `İstanbul` | `istanbul` |
| `Mac & Cheese` | `mac-cheese` |
| `Kid's menu` | `kid-s-menu` |
| `Canard à l'orange` | `canard-à-l-orange` |
| `🍕 Pizza` | `pizza` |
| `cafe` + U+0301 | `café` |
| `2 für 1` | `2-für-1` |
| `ΟΔΟΣ` | `οδος` |
| `ラーメン`, `चाय`, `ψάρι` | unchanged |
| `!!!`, `🍕` | empty. A body gets `422`, and a query or path value gets `400`. |
| more than 63 characters after the change | `422` in a body. The API does not cut a tag. |

- the API does not merge texts that differ only in their accents. `café` and `cafe` are two tags. Accents can change the meaning of a word, such as `año` and `ano`.
- the tag input shows the existing `café` first when a user types `cafe`. The user then picks it or adds `cafe`.
- the tag filters and `getTag` change their values in the same way. They compare whole names, so `tags[has]=cafe` does not find `café`.
- the responses have the stored names. A client sees the form that the API saved.

## The tag list

| Parameter | Values |
|---|---|
| `search` | the start of the name or of a word of the name. `fired` finds `wood-fired`. |
| `kind` | `restaurants` or `recipes`. A tag without a subject of the kind is not in the list. |
| `sort` | `-count`, the default, `count`, `name`, or `-name`. The `name` sort compares code points. |
| `limit`, `cursor` | the pages of decision 00001 |

- `search` has 1 to 63 characters. It gets the steps of [Tag names](#tag-names). A search without a letter or a digit gets an empty list, not an error. The UI sends the text as the user types it.
- the search ignores case and accents, like the other searches. `Cafe` finds `café`.
- a separator in the search matches a hyphen. `wood f` and `Wood_F` find `wood-fired`.
- `-count` uses the sum of both counts. With `kind`, it uses the count of the kind. `name` breaks a tie.
- a tag with exactly the name of the changed `search` comes first in each sort. It is in the list also when only the other kind has it. The tag input then finds an existing tag before it offers a new one.
- a tag with the same name without accents comes next. `?search=cafe` has `cafe`, then `café`, then `cafe-bar`.

## A save with a new tag

Ana adds the restaurant "Forno" with the tags `Pizza` and `Wood Fired`.
`pizza` exists. `wood-fired` does not.

- the save changes the texts to `pizza` and `wood-fired`
- the save makes the tag `wood-fired` and refers to both tags
- the response has `"tags": ["pizza", "wood-fired"]`
- the create limit and the edit limit of decision 00003 count the save. A new tag adds no count.

A repeat in one request is one tag. The first one stays in its place.
`["Pizza", "pasta", "pizza"]` gives `["pizza", "pasta"]`. The API does not return `422` for a repeat.
The limit of 20 counts the tags after the change. 21 texts with one repeat give 20 tags.

Ana then removes `wood-fired` from "Forno". No other subject has it.
The save deletes the tag. The tag input does not suggest it again.

## The UI

- the tag input of the restaurant form and the recipe form opens a list of suggestions on focus. The list has the most used tags of the kind.
- typing changes the suggestions. Each suggestion has the name and the count.
- the input changes the typed text to a tag name. A text without an existing tag of that name gets the option "Add new tag ‘name’" with the changed name. Ana types `Wood Fired` and sees "Add new tag ‘wood-fired’".
- Enter adds the changed name. The chip shows `wood-fired`, and the live region says "Added wood-fired".
- an existing tag with the same name without accents comes first, but the option for the new tag stays. A user who types `cafe` sees `café` and "Add new tag ‘cafe’".
- the input shows an error only for an empty name, a name of more than 63 characters, a repeat, or more than 20 tags
- the hint of the "Tags" field tells the user that the app changes the text. Tags are saved in lowercase with hyphens.
- the tag filter of the restaurant and recipe pages has the same input. It suggests only existing tags and has no "Add new tag" option.
- each tag on a restaurant page or a recipe page links to `/tags/{name}`
- the tag page has the name of the tag, `KindSwitch`, and a section for restaurants and a section for recipes. Each section has the highest overall first, like the menu of a list in decision 00006.
- the tag page changes a route such as `/tags/Wood%20Fired` to `/tags/wood-fired`

## A superuser fixes a tag

Two users added `woodfired` and `wood-fired`.
The superuser opens `woodfired` in the dashboard and changes each of its subjects to `wood-fired`.
The superuser then deletes `woodfired`.

A rename to a name that exists gets the error of the unique index. A merge needs the steps above.
The dashboard changes a typed name to a tag name. A superuser who types `Wood Fired` gets `wood-fired`.
The relation picker of the dashboard shows only existing tags. A superuser makes a new tag in the `tags` collection first.

# Implementation Details
[implementation-details]: #implementation-details

## Collections

| Collection | Fields |
|---|---|
| `tags` | `name`, `name_key`, `created` |

- `name` is a required text field with the `Tag` pattern and a maximum of 63. `idx_tags_name` is a unique index on it.
- a record hook changes `name` to a tag name before the validation. A save in the dashboard also gets it.
- `name_key` is the name in lowercase without the marks of category `Mn`. A record hook sets it on each save. It serves the search of `listTags`.
- the API rules are `null`. Only superusers use the collection through the PocketBase API.
- `tags` of `restaurants` and `recipes` is a relation to `tags` with a maximum of 20. It has no cascade delete.
- an empty relation is `[]` in the database. The API returns `null`, as decision 00004 requires.

## Tag names

- the package `app/api/internal/tagname` has `Of`, `Key`, and `List`. The Public API and `webui` use it.
- the migrations have copies of `Of` and `Key`. A migration does not change when the code changes.
- `Of` changes a text to a tag name with the steps of [Tag names](#tag-names). It can give an empty name.
- `Key` gives `name_key`. It replaces `tagKey` of the Public API.
- `List` changes each text with `Of`, drops the empty names, and removes the repeats. The first one stays in its place.
- Go has no table of `Default_Ignorable_Code_Point`. `Of` derives it from `Other_Default_Ignorable_Code_Point`, `Variation_Selector`, and `Cf`, like Unicode does.
- `SearchKey` gives the key of `listTags`. It keeps the `σ` of an unfinished last word. A separator at the end adds a hyphen, so `wood ` does not find `woodland`.
- `toTag` of `app/ui/src/lib/validation.ts` has the same steps. It replaces `suggestTag`. `isTag` is true for a stored name.
- the lowercase rules of Go and JavaScript differ for some letters, such as `İ` and the Greek final sigma. `toTag` changes each code point to lowercase, like Go. It changes `İ` to `i` itself.
- `specs/api/tag-names.json` has a `text` and a `tag` for each case. The Go tests and the Vitest tests both read it. A difference of the two functions fails a test.

## The spec

- the `Tag` schema keeps its pattern and its length of 1 to 63. The pattern is the stored form.
- the extension `x-tag: true` of `Tag` replaces `x-nfc`. The request code changes the value with `tagname.Of` before the validation.
- `x-tag` covers the bodies of `createRestaurant`, `updateRestaurant`, `createRecipe`, and `updateRecipe`. It also covers `tags[has]`, `tags[has_any]`, `tags[has_all]`, and the path parameter `tagName`.
- the extension `x-tags: true` of the `Tags` array also removes the repeats after the change
- `Tags` keeps `uniqueItems: true`. The validation comes after the change, so it passes. The description of `Tags` says that the API removes the repeats.
- `maxItems` and `maxLength` then count the changed tags
- an empty name fails `minLength: 1`. Its `x-pattern-message` is "must have a letter or a digit".
- the description of `Tag` lists the steps and has examples. A client that sent only valid tags gets the same result.
- `search` of `listTags` keeps `x-nfc`. `ListTags` changes it with `tagname.Of`, because an empty result is not an error there.

## Tag tables

- `restaurant_tags` and `recipe_tags` keep one row for each tag of a subject. Their `tag` column has the ID of the tag record.
- the triggers of decision 00004 keep the tables equal to the records. They read the IDs of the relation with `json_each`.
- `tags[has_any]=a&tags[has_any]=b` adds `restaurants.id IN (SELECT restaurant FROM restaurant_tags WHERE tag IN (SELECT id FROM tags WHERE name IN ('a', 'b')))`
- an unknown tag in a filter matches no subject. A filter value without a letter or a digit gets `400`.
- the counts of a tag come from the tag tables. The tables have the index on `tag` from their primary key.

## The migrations

`1795737600_tags.go` is the migration of the relation. `1794096000_init.go` does not change. See decision 00002.

1. It makes the `tags` collection.
2. It reads the tags of each subject into memory. It keeps only the strings of the JSON arrays.
3. It inserts one tag record for each distinct name with SQL.
4. It drops the tag triggers. SQLite refuses the field change with them.
5. It replaces the `json` field `tags` with the `relation` field `tags` at the same position. PocketBase drops the old column. PocketBase refuses a change of the type of a field.
6. It writes the IDs of each subject with SQL. The `updated` time stays, and no version is written.
7. It makes the triggers again and fills the tag tables with the IDs.

The down migration writes the names back into a `json` field in the order of the relation. It then deletes the collection.

`1796342400_tag_names.go` changes the existing names to the new rules. All of them have the old `Tag` pattern. NFKC changes a few of them, such as fullwidth letters, ligatures like `ﬁ`, and modifier letters like `ʰ`.

1. For each tag, it gets the new name with `tagNameOf`, the copy of `tagname.Of`. It skips the tags that do not change. A name that grows to more than 63 characters stays.
2. If no tag has the new name, it sets `name` and `name_key` with SQL.
3. If a tag has the new name, it merges the two. The older tag stays. It changes the ID of the other tag to the kept ID in the `tags` JSON of each subject and removes the repeats in their order. Then it deletes the other tag.
4. The triggers change the tag tables. The migration writes the new names into the `tags` column of the FTS5 rows of the changed subjects.
5. The `updated` time stays, and no version is written.

Its down migration changes nothing. A merge cannot be undone.

The `snapshot` of the versions keeps the names. It does not change. An undo sends an old name again, and the API changes it to the stored form.

## Server

- `recordvalues.ExpandTags` loads the tag records of the relation. `recordvalues.Tags` gives their names in the order of the relation. The Public API, `searchindex`, and `Kind.Snapshot` use them. The API values and the versions do not change.
- `ExpandTags` first removes the old expand. PocketBase keeps an old expand when the relation is empty.
- `resolveTags` of `tags.go` gets the ID of each name in the transaction of a create or an update. It makes a tag record for each missing name.
- the tags come after the place check and the source check. A conflict then makes no tag.
- `resolveTags` uses `SaveNoValidate`. The spec validation checked the names.
- the handlers change the tags with `tagname.List` also without the spec validation. With `REVIEWS_VALIDATE_REQUESTS=false`, an empty name is dropped, and a name of more than 63 characters stays, like the other values.
- the relation keeps its limit of 20 also without the spec validation. More than 20 tags after the change get `422` with an error of `tags`.
- `idx_tags_name` stops a second record for one name when two saves make the same tag at the same time
- `restaurantguard.go` and `recipeguard.go` check the tags of a dashboard save as IDs of existing tags. They then give the names to the checks of `RestaurantCreate` and `RecipeCreate`.
- `searchindex` writes the names of the tags into the `tags` column of the search tables. The record has only the IDs.
- a record hook of `restaurants` and `recipes` deletes the removed tags without a subject. It runs in the transaction of the save or the delete. A save in the dashboard also gets it.
- `tagguard.go` gives a save of a tag in the dashboard the checks of `Tag`. The record hook changed the name before these checks.
- a rename of a tag in the dashboard updates the search tables of its subjects. Their `tags` column has the names. See decision 00002.
- a rename also writes a version with the source `admin` for each subject with the tag. Without it, the next version of a user shows a change of `tags`.
- a delete of a tag in the dashboard removes its ID from each subject. PocketBase 0.40 calls `SaveNoValidate` for each subject, so each one gets a version with the source `admin`.
- the record hook of unused tags deletes with SQL. PocketBase deletes the row of a tag before it saves the parents. The hook then finds no row of that tag.
- `recordvalues.ParentsWithTag` finds the subjects of a renamed tag for `history` and `searchindex`
- `listTags` keeps a tag when an `EXISTS` finds a row of it in a tag table of the kinds. The counts of the sort and the response come only for these tags.
- the first sort key ranks the exact name 2 and the same `name_key` 1, in descending order. It is one key, so a cursor keeps its number of keys. A tag of this rank needs an `EXISTS` in any tag table.
- the search of `listTags` changes the text with `tagname.SearchKey`. It compares `name_key` with `LIKE 'text%'` and `LIKE '%-text%'`. `%` and `_` are escaped.
- a tag of the first sort key passes the search too. `οδοσ` finds `οδος`, because `Of` changes the last `σ` and `SearchKey` keeps it.
- the `tags` table is small. The search reads all rows.
- `x-tag` also changes the path parameters. `getTag` then finds `café` with `cafe` + U+0301 and `wood-fired` with `Wood Fired`.
- `tagMeta` of `pagemeta.go` changes the path value with `tagname.Of` before it finds the tag. `/tags/Wood%20Fired` gets the link preview of `wood-fired`.
- a new kind of subject adds its tag table, a count property, and a value of `kind`

## The UI

- `TagInput` follows the combobox pattern of WAI-ARIA. The input has the role `combobox`. The suggestions are a `listbox` with the name "Suggestions".
- the listbox name has no "tags". `getByLabel('Tags')` of the end-to-end tests would find it too.
- the name of each suggestion is its text, such as "wood-fired, 4 restaurants". The comma is in a `sr-only` span. An `aria-label` would differ from the visible text. Axe refuses that in WebKit.
- the prop `suggest` gets the suggestions. `tagSuggester` of `lib/tags.ts` calls `listTags` with `kind`, the default sort `-count`, and a limit of 8. `TagInput` waits 200 ms after the last key.
- `listTags` puts a tag with the exact name first, also when it is not in the most used. "Add new tag" then does not show for an existing tag.
- `TagInput` compares `toTag` of the typed text with the suggestions. The option "Add new tag" hides only for a suggestion with exactly that name.
- `TagInput` changes the text with `toTag`. `checkTag` then checks the name. It gives the errors of [The UI](#the-ui) only.
- `useListQuery` changes the `tags` of a link with `toTag`. `?tags=Wood%20Fired` filters by `wood-fired`.
- `tagSuggester` of a filter has `onlyUsed`. It drops an exact tag that only the other kind has. Its filter would show nothing.
- while the suggestions of a new text load, the arrow keys select nothing. The list can still show the old options. Enter then adds the typed text.
- Enter adds the selected suggestion. Without a selected suggestion, it adds `toTag` of the typed text. A mouse click on a suggestion keeps the focus in the input.
- a suggestion keeps the name of the API. `toTag` changes only typed text. A difference of the Unicode versions of Go and the browser then makes no second tag.
- the prop `allowNew` adds the option "Add new tag ‘name’". It is on by default. `FilterBar` turns it off.
- the option shows only for a name that `checkTag` accepts. A name of more than 63 characters gets no option.
- the prop `openOnFocus` shows the most used tags on focus. It is on by default. `FilterBar` turns it off, because the popover focuses the input when it opens. Typing or ArrowDown then opens the suggestions.
- without `openOnFocus`, a pick closes the list. In a form, the list shows the most used tags again after a pick.
- `TagPage.vue` has the route `/tags/:name`. Each section loads `listRestaurants` or `listRecipes` with `tags[has]` and `sort=-overall`. Each section has its own "Load more".
- `TagPage.vue` replaces the route with `toTag(name)` when it differs. It loads with the changed name, so the replace sends no second request.
- a section loads its list when `KindSwitch` shows it, one time for each tag. A hidden section sends no request.
- the sections do not merge the two lists. The `overall` sort also uses the number of reviewers, so the UI cannot compare a restaurant with a recipe. See decision 00005.
- a tag name that the API refuses gets the not found page, like an unknown tag
- `ParentCard` shows the tags as text. The card is one link, and a link cannot have a link in it.
- `pagemeta.go` of `app/api/internal/webui` writes the title of the tag page. See decision 00002.
- `specs/design-system/components/TagInput` describes the suggestions, the change of the text, and the "Add new tag" option

# Alternatives
[alternatives]: #alternatives

| Alternative | Result |
|---|---|
| The names stay in the subjects, and `tags` is only a list of the names | Not selected. A rename would change each subject with the tag. |
| Tag IDs in the Public API | Not selected. The SDKs, the UI, the filters, and the versions would change. The name is already unique. |
| Only existing tags on a subject, and a `createTag` operation | Not selected. A user would leave the form to add a tag. |
| A new tag only from the dashboard | Not selected. A superuser would need to act before each new tag. |
| One operation that lists the restaurants and the recipes of a tag | Not selected. It needs a `oneOf` of both kinds and a cursor over two tables. The UI loads the two lists. |
| One merged list of both kinds on the tag page | Not selected. The `overall` sort cannot compare a restaurant with a recipe in the UI. |
| A rename, a merge, and a delete in the Public API | Not selected. A superuser does them in the dashboard. |
| Tags without a subject stay | Not selected. The input would suggest each removed typo. |
| An FTS5 table for the search of `listTags` | Not selected. The `tags` table is small, and it needs more triggers. |
| `TagsInput` and `Combobox` of reka-ui for the tag input | Not selected. The custom combobox keeps the checks, the blur, and the Backspace of `TagInput`. |
| Strict tag input with `422` and a suggestion of the valid form | Removed. Users had to type the stored form again. |
| `422` for a repeated tag | Removed. The user meant one tag. |
| One tag for `café` and `cafe` | Not selected. Accents can change the meaning of a word, such as `año` and `ano`. A merge cannot be undone. |
| Remove the apostrophes | Not selected. French and Italian names such as `l'orange` lose a word break. |
| Cut a long tag at a word | Not selected. A cut tag can lose its meaning. |
| Keep the case of the first user, such as `BBQ` | Not selected. It needs a display name and a key, and it changes the tag URLs. |
| A separate request schema for free text | Not selected. The `Tag` schema already describes the stored form, and `x-nfc` already changed values before the validation. |
